# Agent-Session-Relay v0.8.0

Relay now supports native Codex and Claude Code lifecycle hooks alongside Kiro. This release also
fixes the macOS CI failure in the multi-repository rollback test.

## Codex and Claude Code

```bash
relay codex install --global
relay claude-code install --global
```

Use `--project` instead inside a target Git repository to share hooks with that repository.
`relay claude` is an alias for `relay claude-code`.

- Codex uses `.codex/hooks.json`; Claude Code uses `.claude/settings.json`. Global installation
  honors `CODEX_HOME` and `CLAUDE_CONFIG_DIR`, respectively.
- Installation merges the three Relay lifecycle handlers into existing JSON files, preserving
  other hooks, permissions, and settings. Reinstalling identical hooks does not rewrite files.
  Customized Relay entries require `--force`; malformed JSON and symlinks are never overwritten.
- `UserPromptSubmit` performs the existing review handoff and injects structured Relay context.
  `Stop` leaves ordinary proposals unstaged and restores unexpected BTW writes with a JSON warning.
  `PreToolUse` applies the shared Git/lifecycle/write guards to native tool payloads.
- Single-repository and multi-repository sessions use the same review and recovery core.
  Conversation IDs distinguish the new harnesses; child lifecycle events do not close parent turns.
- Kiro retains its existing standalone v1 hooks, output contract, and stored conversation IDs.

Ensure `relay` is on the harness's PATH and start a new harness session. Codex requires the Relay
hooks to be reviewed and trusted in `/hooks`; project hook configuration also needs project trust.
Use a current Codex with native lifecycle hooks; old notify-only versions are unsupported.
Project hook files must be committed before `relay start`. Global installation is recommended
when launching a multi-repository session from its non-Git parent directory.

See [Codex setup and smoke test](../codex.md) and [Claude Code setup and smoke test](../claude-code.md).
The command guard remains a workflow aid rather than an arbitrary-program sandbox. After manually
interrupting the agent, run `relay end-interrupted-agent-turn` before reviewing; automatic interrupt
cleanup and background-process coordination are not installed.

## macOS CI repair

The v0.7.1 [CI run](https://github.com/Vopaaz/Agent-Session-Relay/actions/runs/35816320320) failed on
both macOS Python jobs because its injected second-member failure compared an unresolved temporary
path with Git's canonical path. On macOS, `/var/...` and `/private/var/...` refer to the same directory,
so the intended exception never occurred.

Fixtures now resolve temporary roots, and failure injection compares canonical member paths.
A regression case routes the workspace through a symlink, verifying that failure in the second
member restores every member's HEAD, staged contents, and unstaged edits. The macOS CI matrix and
rollback assertions remain enabled.

## Compatibility and validation

The package version is `0.8.0` and the Git tag is `v0.8.0`. Per-worktree schema 2 and workspace schema 1
are unchanged; existing sessions need no migration. Kiro hooks do not need to be reinstalled.
New tests cover native hook JSON, guard denials, duplicate events, malformed input, ownership,
settings merges, BTW restoration, multi-repository sessions, and both adapters in the zipapp.
Live agent conversation smoke tests are documented separately and are not part of automated CI.

Upgrade with `pipx upgrade agent-session-relay`, or replace the standalone archive. Users upgrading
from v0.2.x must first follow the [v0.3.0 cleanup instructions](v0.3.0.md#upgrading-from-v02x).

## Maintainer release commands

From this checkout, after reviewing the changes:

```bash
. .venv/bin/activate
python -m unittest discover -s tests -v
ruff check .
python scripts/build_pypi.py --tag v0.8.0
python scripts/build_zipapp.py
```

Commit the source and release notes, then push the release tag:

```bash
git add src tests docs README.md README.zh-CN.md CONTRIBUTING.md SECURITY.md pyproject.toml
git commit -m "Release v0.8.0"
git push origin master
git tag -a v0.8.0 -m "Agent-Session-Relay v0.8.0"
git push origin v0.8.0
```

The tag workflow checks the version, runs tests/lint, builds all four artifacts, and creates a
draft GitHub release. It does not upload to PyPI. Inspect the draft and CI, then publish explicitly:

```bash
python scripts/build_pypi.py --tag v0.8.0 &&
python -m twine upload \
  dist/pypi/agent_session_relay-0.8.0-py3-none-any.whl \
  dist/pypi/agent_session_relay-0.8.0.tar.gz
gh release edit v0.8.0 --draft=false
```

Twine uses your configured PyPI credentials or prompts for a token. No credentials belong in the
repository. To rehearse, add `--repository testpypi` to the Twine upload command instead.
