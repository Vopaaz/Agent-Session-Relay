# Agent-Session-Relay v0.10.0

Finish selected repositories without ending the remaining review session, and add several
repositories with one command. Both operations use recoverable group transactions.

## Finish selected repositories

```bash
# From the common parent, during the active session's human phase:
relay repo finish ./package-a ./package-b -m "Complete these packages"
```

- At least one target is required. Targets can be registered repository names or cwd-relative
  worktree roots, and must identify distinct current members.
- Only selected repositories must be fully reviewed. Other members can retain staged approvals,
  unstaged changes, and untracked files. Inactive, suspended, and agent-phase calls are rejected.
- Changed targets receive the same result commits and result branches as `relay finish`, with
  each commit parented by that member's immutable base. Unchanged workspace members return to
  their origin without an empty commit.
- Finished repositories leave the session. Their local session state, review refs, membership,
  and message overrides are removed in the same transaction. A failure rolls back the entire
  batch, including result refs and membership changes.
- Remaining members retain their review state, session ID, workspace root, turn numbering,
  next-turn mode, and conversation ownership. A single remaining member stays in the workspace;
  finishing the last member ends the session. Other suspended sessions keep their own scope.
- Message priority remains the member override, this command's `-m`, then the saved shared message.
  Only selected members need messages. When editing is needed, the first selected member in
  repository-name order supplies Git editor/template configuration. Input applies only to this
  finish and does not change the remaining session's messages.
- Later status, diff, suspend, resume, finish, and abort cover only remaining members. Re-adding a
  completed repository starts a new membership period from its current HEAD; its earlier result
  is not folded into the new result commit or undone by a later abort.
- In a standalone session, `relay repo finish .` finishes that session like `relay finish`, with
  the human-phase requirement of `repo finish`.

Discovery and Git guard behavior stay unchanged. A completed repository is no longer an entry to
the remaining session. If the agent was started there, start a new agent session from the common
parent or a remaining member; the command prints a reminder when its cwd leaves the session.
An active workspace's guard still blocks direct agent Git commands targeting unrelated repositories.

## Add several repositories at once

```bash
# From an existing member, during the human phase:
relay repo add ../package-a ../package-b ../package-c
```

All paths are validated before enrollment, and all additions share one transaction. Invalid,
duplicate, overlapping, dirty, or already-active targets prevent the entire batch from being added.
Standalone promotion computes the nearest common parent using the original repository and every
new path. Single-path calls remain supported; an existing workspace keeps its root.

## Compatibility and upgrading

The package version is `0.10.0` and the Git tag is `v0.10.0`. Per-worktree and workspace coordinator
metadata remain schema 2. Existing v0.9.0 active and suspended sessions require no migration, and
hooks do not need to be reinstalled. Legacy workspace state/journal readers remain available as
described in the [v0.9.0 upgrade notes](v0.9.0.md#upgrading-from-v08x).

After publication:

```bash
pipx upgrade agent-session-relay
relay --version
relay repo finish --help
```

The version should report `0.10.0`. Standalone users can replace `relay.pyz` with the new archive.
See [multi-repository sessions](../workspaces.md) for scope, messages, and recovery details.

## Validation

Release checks cover the full automated suite, Ruff, strict wheel/source-distribution metadata
validation, standalone archive execution, and installed-wheel smoke checks. The new workflow tests
exercise partial and batch completion, remaining review state, message editing and revalidation,
human-phase restrictions, standalone promotion, linked worktrees, suspended-session isolation,
re-enrollment, ordinary rollback, and crash recovery before and after the durable commit decision.

## Maintainer commands

Build and validate locally:

```bash
. .venv/bin/activate
python -m unittest discover -s tests -v
ruff check .
python scripts/build_pypi.py --tag v0.10.0
python scripts/build_zipapp.py
```

The artifacts are:

- `dist/pypi/agent_session_relay-0.10.0-py3-none-any.whl`
- `dist/pypi/agent_session_relay-0.10.0.tar.gz`
- `dist/relay.pyz`
- `dist/relay.pyz.sha256`

Commit the prepared source, tests, and release notes, then push the release tag:

```bash
git add src tests docs README.md README.zh-CN.md CONTRIBUTING.md
git commit -m "Release v0.10.0"
git push origin master
git tag -a v0.10.0 -m "Agent-Session-Relay v0.10.0"
git push origin v0.10.0
```

The tag workflow runs validation and creates a draft GitHub release containing all four artifacts.
It does not upload to PyPI. Rebuild and upload only the matching distributions:

```bash
python scripts/build_pypi.py --tag v0.10.0 &&
python -m twine upload \
  dist/pypi/agent_session_relay-0.10.0-py3-none-any.whl \
  dist/pypi/agent_session_relay-0.10.0.tar.gz
```

After the tag workflow succeeds, publish the GitHub draft:

```bash
gh release edit v0.10.0 --draft=false
```
