# Agent-Session-Relay v0.9.0

Add a repository to an in-flight review session with `relay repo add PATH`. Repository scope now
belongs to each session, and every prompt hook includes the current scope.

## Add a repository during human review

```bash
# From an existing member, during the active session's human turn:
relay repo add ../another-package
```

- The new path must identify a clean, stable Git worktree root with an initial commit and no
  active Relay session. Existing members can retain staged approvals and pending changes.
- Inactive, suspended, and agent-phase calls are rejected. Only the current session changes;
  other suspended sessions retain their own membership, review state, and messages.
- A single-repository session becomes a multi-repository session at the nearest common parent,
  preserving its session ID, base, reviewed checkpoints, staging, and history. Cwd stays unchanged.
- An existing multi-repository session keeps its root. Additions must be below that root, and
  members must remain distinct, non-overlapping worktrees. Linked worktrees are supported.
- New members participate in the next handoff with the session's turn numbering and next-turn
  mode, including BTW, without fabricated earlier snapshots. They use the same member records
  and diff, message, finish, suspend/resume, abort, and recovery logic as initial members.
- Enrollment and standalone promotion use the coordinated recovery journal. Ordinary errors roll
  back; interrupted operations remain discoverable from either member for `relay recover`.

## Session scope and prompt context

Each session's `members` is its sole source of repository scope. The common parent's `.relay/`
directory stores sessions, without a shared repository configuration. `resume` restores the selected
session's scope; new multi-repository sessions explicitly specify `start --repo ...` again. Plain
`relay start` starts a single-repository session in the current Git worktree.

Every prompt hook includes the current repository names and absolute paths, including brief
reminders, continuations, and single-repository sessions. The full review introduction still appears
once per conversation. Lists and explicit session selection keep standalone suspended sessions
accessible from their worktrees after the active session is promoted.

## Upgrading from v0.8.x

Existing active and suspended v0.8.x sessions can continue with v0.9.0. There is no need to finish,
abort, suspend, or recreate a session before upgrading, and existing v0.8.x hooks need no reinstall.

| Metadata | v0.8.x | v0.9.0 behavior |
| --- | --- | --- |
| Per-worktree state in the Git directory | Schema 2 | Remains schema 2; existing records are accepted |
| Multi-repository coordinator state in `.relay/` | Schema 1 | Read as session-owned membership; the next successful mutation writes schema 2 |
| Per-worktree recovery journals | Existing transaction format | Read and recovered using the existing recovery logic |
| Multi-repository recovery journals | Workspace-wide identities and member IDs | Normalized on read, including pending and committed operations |

Inspection does not rewrite legacy metadata. Git refs, session IDs, bases, approvals, snapshots,
turn modes, and conversation ownership survive the upgrade. A retained journal still requires
`relay recover` before normal commands, as it did before the upgrade.

After a coordinator has been written as schema 2, v0.8.x cannot read it; use v0.9.0 consistently
for that session. This is forward compatibility, not support for switching back and forth.

After publication, upgrade and check the installed CLI:

```bash
pipx upgrade agent-session-relay
relay --version
relay status
```

The version should report `0.9.0`. Standalone users can replace `relay.pyz` with the new archive.
See [multi-repository sessions](../workspaces.md) for scope and lifecycle details.

## Validation

The release passes the full automated suite and repository lint checks. Separate upgrade checks
create sessions with the actual v0.8.0, v0.8.1, and v0.8.2 tagged sources and continue them with
the v0.9.0 zipapp. They cover single/multi-repository human and agent phases, suspended staging
and BTW restoration, repository additions, native hook ownership, pending recovery after Git GC,
and cleanup after a committed operation. Release artifacts also receive package metadata and
installed-wheel smoke checks.

## Maintainer commands

Build and validate locally:

```bash
. .venv/bin/activate
python -m unittest discover -s tests -v
ruff check .
python scripts/build_pypi.py --tag v0.9.0
python scripts/build_zipapp.py
```

Commit the prepared source, tests, and release notes, then push the release tag:

```bash
git add src tests docs README.md README.zh-CN.md CONTRIBUTING.md
git commit -m "Release v0.9.0"
git push origin master
git tag -a v0.9.0 -m "Agent-Session-Relay v0.9.0"
git push origin v0.9.0
```

The tag workflow creates a draft GitHub release with the wheel, source distribution, zipapp, and
checksum. It does not upload to PyPI. Publish the prepared distributions and GitHub draft explicitly:

```bash
python scripts/build_pypi.py --tag v0.9.0 &&
python -m twine upload \
  dist/pypi/agent_session_relay-0.9.0-py3-none-any.whl \
  dist/pypi/agent_session_relay-0.9.0.tar.gz
gh release edit v0.9.0 --draft=false
```
